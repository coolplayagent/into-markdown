# Into Markdown 0.0.5：完整真实语料性能与质量对比

测试日期为 2026-09-01（Asia/Hong_Kong）。主机为 Windows 11 x86_64、Intel Core i5-13600KF（14 核 / 20 线程）、31.8 GiB 内存。使用同机正式发布构件，串行运行各工具，所有输入留在本地。

## 主要观察

- OCR off：0.0.5 产生 1,827 个非空结果，比 0.0.4 多 2 个；单次全量扫描为 509.9 秒，对比 528.9 秒（-3.6%）。独立质量代理基本持平。单次扫描受缓存和运行顺序影响，不能把该差值解释为普遍加速。
- OCR auto：0.0.5 产生 1,819 个非空结果，比 0.0.4 多 1 个；全量扫描为 3,325.8 秒，对比 2,635.1 秒（+26.2%）。主要原因是旧版会跳过的内嵌图片现在真正执行 OCR；《绿野仙踪》在 120 秒评测时限下仍记失败，但相同 600 秒补测于 148.2 秒成功。
- AnyDoc 0.2.4 本轮总耗时最短（163.6 秒），但非空结果为 1,512 个、空结果 205 个，峰值 RSS 约 12.0 GiB；MarkItDown 0.1.7 为 1,469 个非空结果、134 个空结果、1,644.7 秒和约 12.1 GiB。工具覆盖范围和执行工作不同，耗时不能脱离覆盖、OCR 与资源限制单独排名。
- 发版前定位并修复了两处明显 OCR 回归：理论区域数被误当成实际文档节点，以及串行图像的临时归一化空间被错误累加。最终产物重新跑完全量语料；除明确记录的 120 秒评测边界和 KML 准入策略变化外，没有发现未解释的明显退化。

## 数据与范围

- 冻结 `real-world-test-data/inventory.csv` 的全部 **2,285** 个输入，重新核验为 **1,979,990,949 字节（1.844 GiB）**；不使用旧报告的 935 文件抽样。
- 清单的四个 CSV 是元数据，不重复当作文档。全部源文件大小与 SHA-256 已核验。
- 2,285 个路径包含 2,206 个不同 SHA-256，79 个重复内容路径仍保留。这是整个目录的工作负载，不能把路径数量解释为独立样本数。以硬链接暂存并用稳定 ID 命名，避免同名输出冲突；原文件不改动。
- 0.0.4 使用已发布 Windows Core，0.0.5 使用本次同源四平台发布流程生成的 Windows Core；不是裸 Cargo 开发构建。
- 两个版本均测试 `--ocr off` 和 `--ocr auto`。auto 是启用内置 OCR 的产品默认策略，保留原生文本并按各格式规则识别栅格图及扫描页面；容器已有原生正文时，内嵌图片仍可能执行 OCR，不等于对已有文本强制重识别。
- 图片在 OCR off 下可能只产生标题或元数据；音视频也可能只输出元数据。这些非空产物不能算作图片文字识别或语音转写成功。
- 保留各版本默认结构和内存预算，`--no-config --jobs 1 --asset-mode omit`，最佳努力策略。0.0.4 在本机自动选择 4 GiB；0.0.5 按物理内存总量、调用时可用内存及系统预留选择预算，本机无压力时为 15.881 GiB。全量表比较各版本默认产品行为，并非相同逻辑内存上限；另有固定 4 GiB 的小样本复测。语音插件不安装；音视频按完整语料列入能力边界，元数据输出不代表转写成功。
- 复用本地 AnyDoc 0.2.4 npm 原生模块、MarkItDown 0.1.7 Python 环境及源码 clone。AnyDoc 禁用 hosted OCR；MarkItDown 禁用插件和网络调用，不使用付费云服务。

## 覆盖、耗时和内存

非空结果仅表示产生了文本产物，不代表正文完整或 OCR 正确；其中包含降级输出，`output-identities.csv` 单列 Core 的 complete/degraded。失败、空输出单独计数。逐文件表的 errorCode 沿用 reasonCode/错误分类，成功结果也可能携带诊断码。耗时包含每组启动、转换和落盘，排除预检、下载、构建和评分；批次中断后的补跑计入测试成本。进程树 RSS 以约 20 ms 采样，可能漏过瞬时峰值。

| 工具 / 模式 | 非空 | 失败 | 空 | 总耗时（秒） | 峰值 RSS（MiB） |
|---|---:|---:|---:|---:|---:|
| 0.0.4 OCR off | 1,825 | 449 | 11 | 528.9 | 1,525.0 |
| 0.0.5 OCR off | 1,827 | 447 | 11 | 509.9 | 1,531.6 |
| 0.0.4 OCR auto | 1,818 | 456 | 11 | 2,635.1 | 1,520.5 |
| 0.0.5 OCR auto | 1,819 | 455 | 11 | 3,325.8 | 1,543.0 |
| AnyDoc 0.2.4 | 1,512 | 568 | 205 | 163.6 | 12,292.4 |
| MarkItDown 0.1.7 | 1,469 | 682 | 134 | 1,644.7 | 12,377.1 |

输入按格式、大小固定排序；小文件每组最多 16 个，超过 5 MiB 单独运行。Core 使用公开批量 CLI；竞品在每组加载一次本地库，逐文件顺序转换。故整组耗时比较的是本次批量使用方式，不是语言或函数的纯微基准。外部监控发现进程树超过 12 GiB 时终止，保留失败并补齐余下输入。

120 秒是本次评测设置的 Core 每输入预算，不是 CLI 默认的固定时限。0.0.4 off 的较早扫描使用整组 120 秒内部截止、单文件 150 秒/多文件 300 秒外部截止，均未触发时限；0.0.4 auto 最早几个短批次也保留旧设置且未触及时限。后续统一按批次输入数扩展：所有工具的外部截止为 150 秒 × 输入数，Core 另设置内部截止 120 秒 × 输入数，避免把排队时间误算为单文件超时。逐批实际设置、耗时和外部终止记录公开于 `deadline-observations.csv`。`memory-budget-observations.json` 汇总实际逻辑内存预算，逻辑预算不等于操作系统 RSS。

## 发版前修复的回归

完整初测发现 18 个 0.0.4 能输出的 EPUB/PDF/PPTX，在原 0.0.5 候选的 OCR auto 模式中被 `documentNodes` 预检拒绝。原因是把每张图最多 3,000 个 OCR 区域乘以引用数，当作实际文档节点；约 35 个图片引用即可能触发 100,000 节点上限，尽管识别内容很少。

[PR #351](https://github.com/coolplayagent/into-markdown/pull/351) 保留完整的工作/输出内存预留和实际节点硬上限，按识别后的真实递归节点数及引用次数，在缓存/复制之前检查；稀疏文字不再因理论区域上限被提前拒绝。

复测还发现《绿野仙踪》EPUB 的 155 张图片被错误地累计了所有临时归一化空间（约 13.995 GiB，单张最大约 0.241 GiB），导致进入 OCR 前请求约 24.65 GB 并被拒绝。[PR #352](https://github.com/coolplayagent/into-markdown/pull/352) 改为预留每张图片的归一化与提供方工作空间之和的最大值；保留输出和引用副本仍全部累计，实际预算与全局错误语义不变。详见 `ocr-memory-regression-fix.json`。

两个修复后的最终正式产物重新跑了全部 2,285 个输入的 off/auto 两组；上述 18 个文件中有 17 个恢复非空结果，逐项身份、正文保留代理与前后状态见 `ocr-node-regression-fix.json`。初测数据、被主动中断的中间候选和旧二进制另行保存，没有混进最终六组汇总。

修复后的 converters、engine、API 三个库测试合计 802 项通过，19 项既有忽略项未改变；PR 的四个 fast gate job 和 14 项工作流策略测试通过。测试源码树与正式构建源码树一致，身份记录见 `final-release-run.json`。

## 复现步骤

在新的空目录中放入本目录的 `scripts/`、`input-manifest.json` 和 `environment.json`，不要把旧 `runs/` 目录带入新的性能测量。使用同一台 Windows 主机、Python 3.13、Node 24，按 `python-dependencies.txt` 创建 MarkItDown 环境；将 `anydoc-package.json`、`anydoc-package-lock.json` 分别复制为独立 npm 目录中的 `package.json`、`package-lock.json`，执行 `npm ci` 安装锁定的 AnyDoc 0.2.4。下载两个发布版的 Windows Core，分别完整解包到 `baseline/`、`candidate/`（包括 PDFium 和许可文件），先核对上述摘要。

```powershell
python scripts/restore_inputs.py --dataset C:/path/to/real-world-test-data
$env:BENCHMARK_PYTHON = "C:/path/to/venv/Scripts/python.exe"
$env:BENCHMARK_ANYDOC_MODULE = "C:/path/to/node_modules/@firecrawl/anydoc/anydoc.js"
& $env:BENCHMARK_PYTHON scripts/run.py into-0.0.4-off into-0.0.4-auto into-0.0.5-off into-0.0.5-auto anydoc markitdown
& $env:BENCHMARK_PYTHON scripts/supplemental.py
& $env:BENCHMARK_PYTHON scripts/analyze.py
```

完整质量重评分还需本地保留证据中的 `oracles/`，应在暂存输入前放入上述目录。没有独立参考时脚本只报告覆盖/性能，不会制造质量分数；公共仓库不分发受限制的源文档、人工抄录或转换正文。`run.py` 可从已有完整批次恢复，已结束的测试记录不会被再次计时。

## 限制

- 全量吞吐是同机单次扫描，受缓存、后台活动和运行顺序影响。明显耗时回归需同输入交错复测，不能仅凭一次比例下结论。
- 本轮性能数字只代表这台 Windows 主机；四平台原生安装验收通过不等于已测量各平台性能。
- 公共测试库包含刻意损坏、加密、空文档、共享字符串放大和边界输入；全量失败率不是普通业务文件失败率。
- 未放宽默认资源限制；大文档拒绝与支持程度、资源安全分别报告。
- 文本代理的归一化忽略标点和数值符号，不能证明公式、负号、小数或所有表格单元格正确；源参考中的数值格式也可能影响分数。
- 本文的文本代理主要衡量参考内容召回，对多余、重复或错误的新增文字惩罚有限；高分不能证明 OCR 没有误识别或虚构文字。
- 非 OCR 文本代理不评价图片保真、复杂图表和公式排版；OCR 另按人工预先核对的图中文字抽检。
